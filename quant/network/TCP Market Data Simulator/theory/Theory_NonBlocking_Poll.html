Non-Blocking I/O { poll() }

Architecture for Phase 3: one thread serves many clients with O_NONBLOCK + poll(). Portable; no epoll/kqueue deep dive, no threads.

01

The Blocking Problem

A blocking accept(), read(), or write() parks the whole process until that one syscall finishes. With one thread:

  • accept() waiting for client B means client A gets no ticks.
  • read() stuck on a slow client stalls everyone else.
  • A full send buffer on one socket blocks the broadcast loop.

For a market-data feed that fans out ticks to N clients, blocking I/O is a non-starter unless you add a thread (or process) per connection — which this project deliberately avoids.

02

O_NONBLOCK

Mark the fd so syscalls return immediately instead of sleeping:

set_nonblock.cpp
int flags = fcntl(fd, F_GETFL, 0);
fcntl(fd, F_SETFL, flags | O_NONBLOCK);

Then accept / read / write either make progress or fail with errno == EAGAIN or EWOULDBLOCK (same meaning on modern systems): not ready — try later. That is not a fatal error; it means “come back when poll says this fd is ready.”

Apply to

Listen socket and every accepted client socket. Set non-blocking right after socket() / accept().

03

poll()

poll() watches many fds and sleeps until at least one is interesting (or the timeout expires):

poll_sketch.cpp
struct pollfd {
    int   fd;
    short events;   // what you care about: POLLIN, POLLOUT, ...
    short revents;  // what happened (filled by kernel)
};

int n = poll(pfds, nfds, timeout_ms);  // -1 = wait forever; 0 = poll
FlagMeaning
POLLINReadable — data, or listen socket has a pending accept
POLLOUTWritable — send buffer has room
POLLERR / POLLHUPError or hangup — drop the client

Level-triggered mindset: if data is still unread, POLLIN stays set on the next poll. Same for POLLOUT while the socket can accept more bytes. You do not get a one-shot edge; keep draining / writing until EAGAIN, then wait again.

Linux has epoll; macOS has kqueue. Better at huge fd counts. We deliberately skip them — poll is portable and enough for this simulator’s client count.

04

Server Loop

One thread, roughly:

  1. Build a pollfd array: listen fd (POLLIN) + each client (POLLIN, and POLLOUT if that client has a pending outbound buffer).
  2. poll(...) with a short timeout so the tick generator / heartbeats can run even when idle.
  3. If listen is readable → accept in a loop until EAGAIN; set new fds non-blocking; add to the client list.
  4. For readable clients → read; on 0 / error → close and remove from the pollfd set.
  5. When a tick (or heartbeat) is due → enqueue bytes per client; write while POLLOUT / until EAGAIN; keep a per-client send buffer for partial writes.
loop_sketch.cpp
while (running) {
    // refresh pfds[] from listen + clients
    int ready = poll(pfds, nfds, tick_timeout_ms);
    if (ready < 0 && errno == EINTR) continue;

    if (listen_readable(pfds[0]))
        accept_until_eagain();

    for (each client) {
        if (readable)  handle_read_or_drop();
        if (writable && has_pending)
            flush_send_buffer();  // stop on EAGAIN / partial
    }

    if (time_for_tick())
        enqueue_tick_to_all_clients();
}
05

poll vs select

Brief: we prefer poll.

  • select is limited by FD_SETSIZE (often 1024) and needs fd-bitmask rebuilds / FD_SET macros each call.
  • poll takes an array of pollfd — no fixed set size in the API, slightly clearer “events / revents” model.

Either works for a handful of clients; poll is the cleaner portable choice for this project’s story.

06

Why Not Threads

Thread-per-client (or a thread pool) would also keep clients from blocking each other, but for this project:

  • Adds mutexes / shared state around the tick fan-out — noise we do not need for the CV story.
  • Harder to reason about than one event loop when the workload is “broadcast the same bytes to N sockets.”
  • The learning goal is multiplexing with non-blocking I/O, not concurrency primitives.

PLAN.md: thread pool / thread-per-client is an explicit out-of-scope cut.

07

Project Decision

Architecture

Single-threaded poll() + O_NONBLOCK on listen and client sockets. Treat EAGAIN/EWOULDBLOCK as “wait for poll.” Buffer partial writes per client. Skip epoll/kqueue and threads — portable and enough for the market-data simulator.

08

Pitfalls

✕

Busy-loop without a poll timeout

Calling poll(..., 0) forever (or spinning on non-blocking reads) burns a core. Use a positive timeout so idle time sleeps and tick/heartbeat deadlines still fire.

✕

Forgetting to remove closed fds

After close(), drop the client from your list and the next pollfd array. Leaving a closed fd in poll causes spurious events or EBADF.

✕

Ignoring partial writes

write may send fewer bytes than requested. Keep a per-client outbound buffer; only clear it after the full message is flushed. Otherwise ticks corrupt mid-stream.
