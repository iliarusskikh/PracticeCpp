Sockets { TCP & Berkeley API }

Baseline for this project: blocking TCP echo today; market-data feed over the same Berkeley sockets tomorrow. Maps the API calls already in server.cpp / client.cpp.

01

TCP vs UDP

Both sit on IP. The difference that matters for this project is delivery semantics:

TCP (SOCK_STREAM)UDP (SOCK_DGRAM)
ConnectionYes — handshake, then a sessionNo — fire datagrams
ReliabilityRetransmits; in-order deliveryBest-effort; can drop / reorder
BoundariesByte stream (no message edges)Datagram = one message
Typical feed useRecovery channels, session-oriented feedsMulticast market data (A/B feeds)

This learning project uses TCP: reliable, ordered delivery so we can focus on framing, binary layout, poll(), and reconnect — without also inventing loss recovery. UDP/multicast market data is a different project.

03

Byte Stream — No Message Boundaries

TCP delivers an ordered stream of bytes. One send() on the peer is not one recv() on yours. The kernel may coalesce or split writes arbitrarily.

  • Echo strings “work” by accident: short messages + blocking read often return everything in one go.
  • A binary market-data protocol cannot rely on that. You need framing — knowing where a message starts and ends.
  • This project chooses fixed-size messages (TICK / HEARTBEAT): loop until sizeof(msg) bytes are read. See Binary Protocol.
Interview trap

“I sent one struct, so one recv gets one struct” is false on TCP. Always plan for partial reads (and, in general, partial writes).

04

SO_REUSEADDR and TIME_WAIT

After close(), a TCP endpoint can linger in TIME_WAIT so delayed packets from the old connection don’t confuse a new one. That can hold the local IP:port for tens of seconds — restarting the server then fails with “Address already in use.”

SO_REUSEADDR (already set on server_fd before bind) lets the listening socket bind again while a prior instance’s sockets are still in TIME_WAIT. Not fatal if setsockopt fails — but bind will then be flaky on quick restarts.

server.cpp (already present)
int opt = 1;
setsockopt(server_fd, SOL_SOCKET, SO_REUSEADDR, &opt, sizeof(opt));
// then bind(server_fd, ...)

Different problem from TCP_NODELAY (Nagle / latency) — see Socket Options & Nagle.

05

htons and inet_pton

Network protocols use big-endian (“network byte order”). Hosts (Apple Silicon, x86) are usually little-endian — so ports and multi-byte integers need conversion helpers.

  • htons(PORT) — host to network short; used for sin_port on both server and client.
  • htonl / ntohs / ntohl — same idea for 32-bit and receive path; binary ticks will use these too.
  • inet_pton(AF_INET, "127.0.0.1", &serv_addr.sin_addr) — presentation → network; modern replacement for inet_addr. Returns ≤ 0 on bad string.
client.cpp (pattern)
serv_addr.sin_family = AF_INET;
serv_addr.sin_port   = htons(PORT);
if (inet_pton(AF_INET, SERVER_IP, &serv_addr.sin_addr) <= 0) {
    // invalid address string
}

Server uses INADDR_ANY (bind all interfaces) instead of a specific IP string — no inet_pton needed there.

06

Project Decision

Locked for this repo

TCP + Berkeley sockets for a learning market-data feed: reliable ordered stream, fixed-size binary framing next, then non-blocking poll(). Not UDP/multicast. Not a full exchange stack — TICK + HEARTBEAT only. Current code is the blocking echo baseline that already exercises the lifecycle above.

07

Quick Reference & Pitfalls

CallRole
socketCreate fd (AF_INET + SOCK_STREAM = TCP)
bindServer: claim local IP:port
listenServer: mark passive; set backlog
acceptServer: new connected fd (blocks until peer)
connectClient: active open / handshake
send / recv / readByte stream I/O
closeRelease fd; starts TCP teardown
setsockopt(SO_REUSEADDR)Faster rebinds after TIME_WAIT
✕

Forgot close()

Leaks an fd. On error paths after socket() / accept() this is easy to miss — Phase 2 SocketGuard exists to fix that pattern.

✕

Bind failed — port in use

Another process holds 8080, or TIME_WAIT without SO_REUSEADDR. Check with lsof -i :8080 / change port.

✕

Connect failed

Server not running, wrong IP/port, or firewall. Client already prints this case.

✕

Assuming message boundaries

One send ≠ one recv. Fixed-size (or length-prefix) framing is required for binary ticks.

✕

Skipping htons

Port bytes swapped on little-endian hosts → connect/bind to the wrong port.
