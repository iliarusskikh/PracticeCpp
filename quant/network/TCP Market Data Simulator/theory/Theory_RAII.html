RAII { Socket fd ownership }

How file descriptors should be owned in this project — acquire in a constructor, close() in a destructor — and what still uses manual cleanup today.

01

Core idea

RAII ties a resource's lifetime to an object's lifetime. For sockets that means: construct → own an int fd; destroy → call close(). C++ runs destructors on scope exit (including early return), so cleanup is not a separate checklist at every exit path.

A small RAII example already in the tree: Timer in include/timer.hpp — start in the constructor, print elapsed time in the destructor. Same pattern; different resource (wall time vs an OS handle).

Scope for this project

TICK + HEARTBEAT over TCP. One thread, poll() + nonblocking sockets. The RAII story here is fd ownership, not mutex locking.

02

Current code

server.cpp and client.cpp still use bare int fds and call close() by hand on every error path and on normal exit.

client.cpp (today) 
int sock = socket(AF_INET, SOCK_STREAM, 0);
if (sock < 0) return 1;

if (inet_pton(...) <= 0) {
    close(sock);   // must remember on this path
    return 1;
}
if (connect(sock, ...) < 0) {
    close(sock);   // and this one
    return 1;
}
// ... send / recv ...
close(sock);       // and the happy path

Same pattern on the server: close(server_fd) / close(new_socket) after bind/listen/accept failures and when a client session ends. Easy to miss one branch as the code grows.

03

SocketGuard sketch

Not implemented yet

SocketGuard is planned for Phase 2 (see PLAN.md). The sketch below is the target design, not code that exists in the repo today.

planned — socket_guard.hpp 
class SocketGuard {
public:
    explicit SocketGuard(int fd) noexcept : fd_(fd) {}
    ~SocketGuard() { if (fd_ >= 0) ::close(fd_); }

    int get() const noexcept { return fd_; }
    int release() noexcept { int t = fd_; fd_ = -1; return t; }

    SocketGuard(const SocketGuard&)            = delete;
    SocketGuard& operator=(const SocketGuard&) = delete;

    SocketGuard(SocketGuard&& o) noexcept : fd_(o.fd_) { o.fd_ = -1; }
    SocketGuard& operator=(SocketGuard&& o) noexcept {
        if (this != &o) {
            if (fd_ >= 0) ::close(fd_);
            fd_ = o.fd_;
            o.fd_ = -1;
        }
        return *this;
    }
private:
    int fd_{-1};
};

Move-only: copy is deleted so two guards cannot own the same fd. Move steals the fd and sets the source to -1 so the moved-from destructor is a no-op.

04

Rule of Zero vs Five

  • Rule of Five — a type that owns a raw resource (like SocketGuard) needs destructor + copy/move ctor + copy/move assign defined together. Default shallow copy would double-close.
  • Rule of Zero — prefer writing none of those on higher-level types. Hold a SocketGuard (and vector, etc.) as members; compiler-generated special members then do the right thing.
connection.hpp (Rule of Zero) 
struct ClientConn {
    SocketGuard sock;           // owns the fd
    std::vector<char> rx;       // owns the buffer
    // no hand-written dtor / copy / move
};
05

Project plan

Phase 2 (PLAN.md) introduces SocketGuard for the listen socket, accepted client sockets, and the client's connect socket — then TCP_NODELAY and light logging alongside it.

  • Later phases add many concurrent clients under a single-threaded poll() loop. Each client fd still needs exactly-one owner; RAII keeps that true when a peer drops mid-parse or a session is removed from the poll set.
  • No multi-threaded shared order book here — do not center the story on std::lock_guard. That tool exists for mutexes; this simulator's resource of interest is the socket fd.
06

Pitfalls

✕

Double-close

If copy is allowed (or move fails to null the source), two destructors call close() on the same number. The second close may hit an unrelated fd the kernel already reused.

✕

Escaping the raw fd

get() is fine for a same-scope send/recv/poll call. Storing that int elsewhere (or calling close() yourself while the guard still owns it) breaks the ownership model.

✕

Manual close + guard

Once wrapped, do not also close(guard.get()) on error paths. Either own via RAII or own via hand-written closes — not both.
