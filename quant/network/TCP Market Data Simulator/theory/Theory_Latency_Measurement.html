Latency { Measurement }

Phase 6 client stats — honest about one-way feed limits, percentiles over means, no HFT clock machinery.

01

What we can measure

This project is mostly a one-way feed: server pushes TICK / HEARTBEAT; the client does not echo. That constrains what “latency” can mean.

MetricHowHonest caveat
Inter-arrival time Client timestamps successive receives with one local clock; delta = gap between ticks Measures client-side spacing / jitter — not wire delay from server
RTT Would need a request/echo path (like the old echo baseline) We largely dropped echo; RTT is optional / not the Phase 6 default story
One-way via server stamp recv_time − tick.timestamp Only meaningful if host clocks are synchronized. Two unsynced machines → garbage deltas
Default for this project

Prefer inter-arrival on the client (one clock, no sync needed). If you print stamp-based one-way, say out loud that it assumes synced clocks — and that you are not claiming PTP/NTP accuracy.

02

Which clock

For local intervals, use std::chrono::steady_clock or high_resolution_clock (often a typedef of steady on this platform). They are monotonic for deltas — wall time can jump with NTP adjustments.

  • steady_clock — preferred for “how long did X take?” / inter-arrival.
  • system_clock — wall time; fine for logging a human timestamp, not for micro-intervals.

Do not claim TSC / rdtsc, cycle pinning, or calibrated CPU clocks. Out of scope for this CV project — knowing they exist is enough if asked.

03

p50 / p99 — why mean lies

Latency distributions are typically skewed: most samples are fine; a few spikes (scheduler, GC-like pauses, Nagle if you forgot TCP_NODELAY, logging) pull the mean up. A mean of 2 ms can hide a p99 of 40 ms.

  • p50 — median; “typical” experience.
  • p99 — 99th percentile; tail that hurts interactive / trading-adjacent systems.

Reporting both is the interview line: you care about the tail, not just the average.

04

Simple approach: store, sort, pick

For this project, keep N samples in a std::vector, sort, read indices. No histogram, no t-digest, no reservoir unless you want extras.

percentile.hpp
double percentile_us(std::vector<double> samples, double p) {
    if (samples.empty()) return 0.0;
    std::sort(samples.begin(), samples.end());
    const size_t i = static_cast<size_t>(
        p * (samples.size() - 1));   // p in [0,1], e.g. 0.99
    return samples[i];
}

// after collecting deltas:
//   p50 = percentile_us(deltas, 0.50);
//   p99 = percentile_us(deltas, 0.99);

Sorting copies or mutating a working buffer is fine at report time (end of run / every N ticks). Hot path: push a double/int64 µs sample — nothing heavier.

05

Project decision

CV talking point

“Phase 6 client reports p50/p99 of inter-arrival times using steady_clock / high_resolution_clock, samples in a vector, sort-and-index. I measure what one local clock can honestly support on a one-way feed — not RTT theatre and not TSC. That shows I know what the metric means and what it doesn’t.”

Deliberately skipped: lock-free timestamp rings, kernel bypass, hardware timestamps, cross-host clock sync. Those belong in a different project.

06

Timer.hpp as a starting point

The tree already has a rough RAII helper in include/timer.hpp: construct → high_resolution_clock::now(); destroy → print elapsed ms. Useful pattern for scoping a timed region.

Evolve it for Phase 6 rather than inventing a parallel story: stop printing from the destructor on every tick (I/O skews the measurement); accumulate samples; report percentiles at the end. Keep the RAII “start on construction” idea if you time parse/recv blocks.

07

Pitfalls

✕

Measuring only in Debug

Unoptimized builds inflate numbers. Document Release (-O2 / -O3) for any stats you quote.

✕

Logging inside the timed path

std::cout / formatting per tick dominates the interval you think you’re measuring. Sample first; print summaries later.

✕

Comparing host clocks without sync

Server stamp − client now across two machines is not one-way latency unless clocks are synchronized. Prefer inter-arrival, or say the caveat.
