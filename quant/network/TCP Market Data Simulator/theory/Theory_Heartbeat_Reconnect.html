Heartbeat { & client reconnect }

Phase 5: detect dead peers with an application HEARTBEAT, then reconnect with backoff. Market-data feed only — no order flow.

01

Why app heartbeat

TCP can leave a half-open connection: one side thinks the socket is fine while the peer has crashed, the cable is gone, or a NAT silently dropped state. Reads may block forever (or sit quiet under nonblocking poll) until the OS eventually notices.

SO_KEEPALIVE exists, but defaults are often on the order of hours and are OS-tunable — too slow for a feed client that should notice a dead server in seconds. An application heartbeat gives a prompt, protocol-level liveness signal we control.

Talking point

"Keepalive is a safety net; our HEARTBEAT is the contract. We want dead-peer detection on our timeout, not the kernel's."

02

Server send / client last_rx

Server periodically emits a fixed-size HEARTBEAT (same binary framing as ticks — see protocol note). Idle clients still see traffic even when no price updates fire.

Client maintains last_rx (or equivalent). Any successfully parsed message — TICK or HEARTBEAT — refreshes it. Busy markets don't need spare heartbeats to prove liveness; quiet markets do.

client sketch 
// after a complete message decode:
last_rx = steady_clock::now();   // tick *or* heartbeat

// in the poll loop:
if (now - last_rx > heartbeat_timeout) {
    // treat peer as dead
}
03

Timeout → reconnect

When now - last_rx exceeds the timeout (a small multiple of the server heartbeat interval is typical):

  1. Close the socket (RAII SocketGuard or explicit close).
  2. Enter reconnect — do not spin forever on a dead fd.
  3. On success, reset last_rx and resume reading.

Same path applies on hard errors (recv returns 0 / fatal errno): close and reconnect; the heartbeat timer covers the silent-death case TCP doesn't surface quickly.

04

Exponential backoff

After a failed connect (or repeated deaths), wait before retrying: e.g. 100 ms → 200 → 400 → …, capped (say 5–10 s), with a max retry count then exit or pause. Prevents reconnect storms when the server is down or restarting.

backoff sketch 
int delay_ms = 100;
const int cap_ms = 5000;
const int max_retries = 20;

for (int attempt = 0; attempt < max_retries; ++attempt) {
    if (try_connect()) break;
    sleep_ms(delay_ms);
    delay_ms = std::min(delay_ms * 2, cap_ms);
}
05

Connection states

Keep a small explicit state machine on the client (Phase 5.4):

StateMeaning
disconnectedNo live socket; may be backing off between attempts.
connectingconnect() in progress (or nonblocking connect pending).
connectedReading ticks/heartbeats; updating last_rx.

Transitions: timeout/error → disconnected → (after backoff) connecting → success → connected. Logging the state makes reconnect behavior interview-visible.

06

Project decision

Locked for this repo

Market-data only. Protocol message types are TICK and HEARTBEAT — heartbeat is a first-class binary message, not a side-channel or TCP option. No ORDER/ACK, no session login. Server pushes heartbeats; client owns timeout + reconnect + backoff.

07

Pitfalls

✕

Only HEARTBEAT counts as alive

If ticks don't refresh last_rx, a healthy busy feed can look "dead" between heartbeat slots — or you fire redundant heartbeats. Refresh on any message.

✕

Reconnect storms (no backoff)

Tight connect loops hammer a restarting server and your own CPU. Cap delay and retries.

✕

Relying on TCP keepalive alone

OS defaults are too slow for feed UX. Keepalive can stay on as a backup; app heartbeat is the primary detector.
