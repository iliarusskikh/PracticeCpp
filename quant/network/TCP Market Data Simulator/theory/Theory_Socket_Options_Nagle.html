Socket Options { Nagle & TCP_NODELAY }

Why small TICK / HEARTBEAT messages need TCP_NODELAY, where to set it in Phase 2, and how that differs from SO_REUSEADDR.

01

Nagle's algorithm

Nagle coalesces small TCP writes: if unacknowledged data is already in flight, the stack holds a new tiny send until an ACK arrives or enough bytes accumulate to fill a segment. That cuts packet count for bulk or chatty byte streams.

For a market-data feed of fixed-size ticks and heartbeats, coalescing adds delay. Each message is already small and latency-sensitive — waiting to batch hurts more than it helps.

02

TCP_NODELAY

TCP_NODELAY = 1 disables Nagle. Set it with setsockopt at level IPPROTO_TCP (not SOL_SOCKET):

  • Level: IPPROTO_TCP
  • Option: TCP_NODELAY
  • Value: int opt = 1

Needs <netinet/tcp.h> for the option name on POSIX.

03

Where we set it

Phase 2 applies TCP_NODELAY on the connected sockets that actually send and receive messages:

  • Server — each fd returned by accept()
  • Client — the socket after successful connect()

Not on the listening socket. Listeners do not carry application data; options often do not inherit to accepted connections the way you might expect.

04

SO_REUSEADDR (already done)

The server already sets SO_REUSEADDR on the listen socket so a restart can re-bind while a previous incarnation sits in TIME_WAIT.

OptionProblem it solvesWhere
SO_REUSEADDRBind / restart vs TIME_WAITListen socket (done)
TCP_NODELAYSmall-message send latencyAccepted + client connect fds

Same API family (setsockopt), different problems. Do not conflate them in interviews or in code comments.

05

Buffer sizes (optional)

SO_RCVBUF / SO_SNDBUF tune kernel socket buffer sizes. Worth knowing exist; for this project we may skip tuning and keep OS defaults. Not required for the CV story.

06

Project decision

Decision

Enable TCP_NODELAY on every data-carrying connection (server accepted clients + client connect socket). Leave buffer sizes alone. Keep SO_REUSEADDR on the listen socket only — already implemented.

07

Code snippet

set_nodelay.cpp
#include <netinet/tcp.h>   // TCP_NODELAY
#include <sys/socket.h>

bool set_tcp_nodelay(int fd) {
    int opt = 1;
    if (setsockopt(fd, IPPROTO_TCP, TCP_NODELAY, &opt, sizeof(opt)) < 0) {
        // log warning; connection still usable with Nagle on
        return false;
    }
    return true;
}

// server: after accept
//   int client_fd = accept(...);
//   set_tcp_nodelay(client_fd);

// client: after connect succeeds
//   set_tcp_nodelay(sock);
08

Pitfalls

✕

Setting NODELAY only on the listen socket

Accepted fds do not reliably inherit TCP_NODELAY from the listener on all platforms. Set it on each accepted connection (and on the client's connect socket).

✕

Wrong setsockopt level

TCP_NODELAY is IPPROTO_TCP, not SOL_SOCKET. Wrong level → silent failure or EINVAL.

✕

Treating SO_REUSEADDR as a latency knob

It only helps bind after restart. It does nothing for tick send latency.
