1
Why Smart Pointers Exist

A raw pointer answers "where is this object" but says nothing about "who is responsible for destroying it." Every bug class below comes from that missing answer:

Leaks

An exception or early return skips the matching delete.

Double frees

Two code paths both believe they own the pointer and both call delete.

Dangling access

Object is freed, pointer is not nulled, something later dereferences it.

Smart pointers bind an object's lifetime to a stack-allocated wrapper's lifetime (RAII). When the wrapper goes out of scope — normally or via exception unwinding — its destructor runs, and cleanup happens automatically. The ownership question gets encoded directly in the type: unique_ptr<T> reads as "exactly one owner," shared_ptr<T> reads as "shared ownership, refcounted."

✓ Rule of Thumb
If you're writing new or delete directly in application code (outside of a smart pointer's own implementation), stop and ask why a smart pointer or container isn't doing it for you.
2
std::unique_ptr

unique_ptr models exclusive ownership. Exactly one unique_ptr instance owns the managed object at any time. It is move-only — copying is disabled at compile time — so ownership can be transferred but never duplicated.

unique_ptr_basics.cpp
1 auto conn = std::make_unique<Connection>(host, port); 2 conn->send(payload); // use like a raw pointer 3 4 auto owner2 = std::move(conn); // ownership transferred 5 // conn is now nullptr — using it is a bug, not UB by itself, 6 // but dereferencing a null unique_ptr IS undefined behavior 7 8 // conn2 = conn; // compile error: copy ctor is deleted

2.1 Key Properties

  • Zero overhead vs. a raw pointer in the common case — no atomic refcount, no control block. It's a thin RAII wrapper around a pointer plus (optionally) a deleter.
  • Always prefer std::make_unique<T>(args...) over unique_ptr<T>(new T(args...)) — it avoids naming new directly and eliminates a leak edge case in function-argument evaluation order.
  • Supports custom deleters via a second template parameter, for wrapping C-style resources (file handles, sockets).
  • Arrays: unique_ptr<T[]> uses delete[] automatically and provides operator[].

2.2 Custom Deleter (a Socket, for Example)

socket_guard.cpp
1 auto deleter = [](int* fd) { close(*fd); delete fd; }; 2 std::unique_ptr<int, decltype(deleter)> sock(new int(fd), deleter); 3 // close(fd) runs automatically when sock leaves scope, 4 // including when an exception unwinds the stack

This pattern — wrapping a POSIX file descriptor so close() is called automatically — is exactly what a SocketGuard-style RAII wrapper does for a Berkeley sockets file descriptor: it turns a manual close(fd) call into a destructor that runs unconditionally.

2.3 Passing to Functions

SignatureMeaning
void f(unique_ptr<T> p)Function takes ownership; caller must std::move in.

void f(T* p) / f(T& t)Function just uses the object, no ownership involved — call with p.get() or *p. This is the most common and idiomatic case.

std::shared_ptr

shared_ptr models shared ownership via reference counting. Multiple shared_ptr instances can point at the same object; the object is destroyed when the last one is destroyed or reset.

shared_ptr_basics.cpp
1 auto a = std::make_shared<Session>(id); // use_count == 1 2 auto b = a; // use_count == 2, copy is allowed 3 { auto c = a; } // use_count -> 3 -> back to 2 on scope exit 4 std::cout << a.use_count(); // 2

3.1 The Control Block

Every shared_ptr group shares one heap-allocated control block holding: the strong reference count, the weak reference count, the deleter, and (for make_shared) the object itself.

FIG 1 — two shared_ptr instances referencing one control block, which owns the object
⚠ Cost
Unlike unique_ptr, shared_ptr is not free: the control block is heap-allocated (unless elided via make_shared), the refcount increment/decrement is atomic (thread-safe refcounting), and the pointer itself is twice the size of a raw pointer (object pointer + control block pointer). Don't reach for shared_ptr as a default — use it only when ownership genuinely needs to be shared.

std::weak_ptr

weak_ptr observes an object managed by shared_ptr without contributing to the strong reference count. It cannot be dereferenced directly — you must first lock() it into a temporary shared_ptr, which is nullptr if the object has already been destroyed.

weak_ptr_lock.cpp
1 std::weak_ptr<Session> observer = session; 2 if (auto locked = observer.lock()) { // promotes to shared_ptr, or null 3 locked->touch(); // safe: locked keeps it alive here 4 } else { 5 // the object is already gone — handle gracefully 6 }

4.1 The Classic Use Case: Breaking Cycles

Two objects holding shared_ptr to each other create a reference cycle — neither strong count ever reaches zero, so neither is destroyed, even when nothing external refers to them. This is a real, common leak pattern (parent/child trees, observer graphs, doubly-linked structures). The fix is to make one direction of the relationship a weak_ptr, typically the "back" pointer (child → parent).

FIG 2 — parent owns child by shared_ptr; child refers back with weak_ptr, so the cycle can't keep both alive
5
Pitfalls & Gotchas
  • Never construct two independent shared_ptr from the same raw pointer — shared_ptr<T>(raw) called twice creates two unrelated control blocks, so the object gets destroyed twice.
  • Calling .get() to obtain a raw pointer is fine for temporary use, but never store that raw pointer somewhere that outlives the smart pointer's ownership.
  • enable_shared_from_this is required if a member function needs to hand out a shared_ptr to *this — constructing one directly from this creates a second, disconnected control block.
  • Passing shared_ptr by value into every function "for safety" is a common overcorrection — it forces an atomic refcount bump on every call. Pass by const& if the callee doesn't need to extend ownership.
  • unique_ptr in a moved-from state holds nullptr — reassign or check before use; dereferencing it is undefined behavior, same as any null pointer.
  • weak_ptr::lock() is the only safe way to access the underlying object; testing expired() then locking separately has a race window in multithreaded code (use the result of lock() directly).
6
Decision Cheat Sheet

Default choice

unique_ptr. Start here for any owned heap resource. Upgrade to shared_ptr only when you can name the second owner.

Need shared ownership

shared_ptr — but confirm the lifetime actually needs multiple owners, not just multiple users.

Non-owning observer

Raw pointer or reference if lifetime is guaranteed by scope; weak_ptr if the object might outlive or be outlived unpredictably.

Breaking a cycle

One direction of a bidirectional owning relationship becomes weak_ptr.
